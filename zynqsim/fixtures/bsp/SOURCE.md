# fixtures/bsp: unmodified Xilinx standalone-BSP applications

The `bsp_*.elf` files are **Xilinx's own software**, built unmodified with Vitis 2022.1 and run by
ZynqSim on the Xilinx QEMU. We author no C: this folder holds the build scripts, the hardware
platform they use, and the resulting ELFs. The Xilinx C sources are **not** in this repository
(they are in the Vitis install: `<Vitis>/data/embeddedsw`). Results of running them are in
`docs/conformance/bsp-apps.md` (ADR-023).

| File | What it is |
|---|---|
| `build_bsp.tcl` | the `xsct` script that builds every ELF (below) |
| `make_ps_all_xsa.tcl`, `zs_ps_all.xsa` | the hardware platform: a PS-only Vivado 2022.1 design (see below) |
| `bsp_*.elf` | the built applications, each < 300 KB (the file size is mostly 64 KB segment alignment padding; `size` says 20-65 KB of code) |

## Toolchain and versions

* Vitis 2022.1 (`C:\Xilinx\Vitis\2022.1`): `bin\xsct.bat` (batch, no GUI), HSI behind it, the
  standalone BSP `lib/bsp/standalone_v7_7`, driver sources `XilinxProcessorIPLib/drivers/*`,
  application templates `lib/sw_apps/{hello_world,peripheral_tests}`.
* Compiler: the Xilinx-shipped `arm-none-eabi-gcc` 11.2.0 (`gnu\aarch32\nt\gcc-arm-none-eabi`),
  `-mcpu=cortex-a9 -mfpu=vfpv3 -mfloat-abi=hard`, `-Os`. The BSP libraries are built by
  `platform generate` from the Vitis install; drivers in the BSP (`zs_ps_all.xsa`):
  canps_v3_6 coresightps_dcc_v1_8 cpu_cortexa9_v2_11 ddrps_v1_2 devcfg_v3_7 dmaps_v2_8
  emacps_v3_16 generic_v3_1 gpiops_v3_9 iicps_v3_15 qspips_v3_9 scugic_v4_7 scutimer_v2_4
  scuwdt_v2_4 sdps_v3_14 spips_v3_7 standalone_v7_7 ttcps_v3_15 uartps_v3_11 usbps_v2_7
  xadcps_v2_6. No `xilffs`/`lwip` library is added (see "Not built" below).
* Newlib's `libc` and `libgcc` from the same toolchain are linked in statically (`print`,
  `xil_printf` and the startup code are Xilinx's own sources in the BSP).
* The ELFs contain no host paths (checked with `strings`).

## Hardware platform

`zs_ps_all.xsa` is written by `make_ps_all_xsa.tcl` (Vivado 2022.1 batch):

```
mkdir C:\zsx            (keep the path short; see fixtures/xsa/make_xsa.tcl)
copy make_ps_all_xsa.tcl C:\zsx\
vivado -mode batch -source C:\zsx\make_ps_all_xsa.tcl -tclargs C:\zsx\psall C:\zsx\psall\zs_ps_all.xsa
```

It is the Zybo Z7-20 PS7 board preset (UART1, QSPI, SD0, ENET0, USB0, GPIO on MIO) plus TTC0,
I2C0, SPI0 and CAN0 on EMIO, **no PL logic**. It exists only so Vitis generates a BSP with the
driver of every PS peripheral a standalone application might use. `stdout`/`stdin` of the BSP
are `ps7_uart_1` (UART1, the Zybo console).

## Build

```
set ZS_WS=C:\scratch\bspws            (an empty scratch directory; it is deleted first)
set ZS_OUT=<repo>\zynqsim\fixtures\bsp
C:\Xilinx\Vitis\2022.1\bin\xsct.bat <repo>\zynqsim\fixtures\bsp\build_bsp.tcl
```

(several minutes; it prints one `BUILT:` line per ELF.) What the script does, in `xsct` terms:

```
platform create -name zsplat -hw zs_ps_all.xsa -proc ps7_cortexa9_0 -os standalone
domain active standalone_domain
bsp config compiler_flags "-Os -c"
bsp config extra_compiler_flags "-mcpu=cortex-a9 -mfpu=vfpv3 -mfloat-abi=hard -nostartfiles -Wall -Wextra -fno-tree-loop-distribute-patterns -ffunction-sections -fdata-sections"
platform generate
app create -name bsp_hello_world      -platform zsplat -domain standalone_domain -template {Hello World}
app create -name bsp_peripheral_tests -platform zsplat -domain standalone_domain -template {Peripheral Tests}
# per driver example: copy ONE file from <Vitis>/data/embeddedsw/XilinxProcessorIPLib/drivers/<drv>/examples/
# into a staging folder, then
app create -name bsp_<x> -platform zsplat -domain standalone_domain -template {Empty Application(C)}
importsources -name bsp_<x> -path <staging folder>
app config -name <app> build-config release
app config -name <app> compiler-optimization {Optimize for size (-Os)}
app build -name <app>
```

The only changes against the Vitis defaults are the optimisation level (`-Os` instead of `-O2`),
`-g` dropped from the BSP flags, `-ffunction-sections -fdata-sections` and the Release
configuration for the applications (no `-g`). No Xilinx source file is edited, patched or
`#define`d around.

## What is in each ELF (all Xilinx sources)

Applications from Xilinx's application templates (Vitis generates / copies them):

* `bsp_hello_world`: `lib/sw_apps/hello_world/src/{helloworld.c,platform.c,platform.h}`.
* `bsp_peripheral_tests`: `testperiph.c` **generated by Vitis** (`lib/sw_apps/peripheral_tests/
  data/peripheral_tests.tcl` + each driver's `*_tapp.tcl`) together with the driver example files it
  copies: `xscugic_tapp_example.c`, `xcanps_polled_example.c`, `xcanps_intr_example.c`,
  `xdevcfg_selftest_example.c`, `xdmaps_example_w_intr.c`, `xiicps_selftest_example.c`,
  `xqspips_selftest_example.c`, `xscutimer_polled_example.c`, `xscutimer_intr_example.c`,
  `xscuwdt_intr_example.c`, `xspips_selftest_example.c`, `xttcps_tapp_example.c`.

Single driver examples, each one file that carries its own `main()` (the driver's

## Licence of the Xilinx sources

The file headers read `SPDX-License-Identifier: MIT` (with "Copyright (c)/(C) ... Xilinx, Inc.") for
the driver sources and examples, the standalone BSP and the Peripheral Tests template; the Hello
World template's files carry the same MIT text written out ("Permission is hereby granted, free of
charge, ..."). A few BSP files (`print.c`, `putnum.c`) are Cygnus Support's permissive newlib-style
notice ("permission to use, copy, modify, distribute ... for any purpose"). The linked `libc` is
newlib and `libgcc` is GCC's runtime (GPLv3 with the GCC Runtime Library Exception). Because the
ELFs contain this code, they are redistributed under those terms; this repository's Apache-2.0
licence covers only the scripts and tests we wrote (`THIRD_PARTY.md` is generated from the Rust
lock files and does not list these ELFs; this file does). The ELFs
are inputs to the simulator, only ever executed by the simulated Cortex-A9.

## Not built, and why

* **lwIP / FatFs applications** (`lwip_echo_server`, FatFs): they need extra BSP libraries
  (`bsp setlib -name lwip211` / `xilffs`) and a second platform generation; not attempted yet.
  `bsp_emacps_intr_dma` (the GEM driver's own DMA example, no lwIP) and `bsp_sdps_raw` (raw SD
  blocks, no FatFs) cover the same controllers at register level.
* `ps7_init`/FSBL: none of these ELFs runs after an FSBL or `ps7_init` (QEMU starts them directly,
  like every other ELF in `fixtures/`); see the conformance document.
