# Unmodified Xilinx standalone-BSP applications on ZynqSim

Prompt §0 success criterion 2: "Unmodified Xilinx standalone BSP applications (UART, GPIO, GIC,
timers, QSPI, SD/FatFs, GEM/lwIP, I2C, SPI, XADC, PL330 DMA) behave as on hardware at register
level". This is the first measurement of it. It was done on 2026-10-16 with Vitis 2022.1 and its
Xilinx QEMU (6.1.0, `arm-generic-fdt-7series`, `zynq-arm-cosim.dtb`), on one machine.

**What "behave as on hardware" can and cannot mean here.** Nothing was compared with a board.
"Passes" below means: the application printed its own success line, i.e. the register behaviour
its driver relied on was present in the QEMU model. "Deviates" means the application failed or
hung and the cause is a property of the QEMU machine (a missing or simplified peripheral), found by
probing the registers; it is not an application bug (the same ELFs are Xilinx's own examples).
The applications are not run behind an FSBL/`ps7_init` (QEMU starts them at reset state, like every
other ELF here).

## How the ELFs were made

Entirely with Vitis 2022.1 batch tools, no GUI and no C of ours. `xsct` generates a standalone BSP
for a PS-only hardware platform (`fixtures/bsp/zs_ps_all.xsa`), builds Xilinx's "Hello World" and
"Peripheral Tests" application templates, and builds one Xilinx driver example per application
(each example file carries its own `main()`). The scripts, the exact commands, the Xilinx source
files and their licences are in `fixtures/bsp/SOURCE.md`. The prototype that preceded this project
used the same route (`build_app.tcl`: `platform create -hw`, `app create`, `app build`) for its own
C sources; here only Xilinx's sources are compiled.

## Where the QEMU machine deviates from the hardware

Found by the applications above and then isolated with a throw-away Rust probe firmware (not
committed) that reads and writes the registers, and by `info mtree` of the same QEMU command line
(the co-simulation machine) with a dummy remote-port peer. Each point is observed behaviour of
this QEMU build; nothing is claimed about other QEMU versions.

**D1. Peripherals that are not in the machine.** The memory map has, among the PS peripherals:
UART0/1, I2C0/1, GEM0/1, QSPI, the PL353 SMC and NAND window, SDHCI0/1, SLCR, TTC0/1, PL330 DMA, an
XADC window (`0xF8007100`, 32 bytes), SCU, GIC (CPU and distributor), global timer, private timer
(`0xF8F00600`, 32 bytes), OCM RAM and the remote-port windows. **Not mapped**, although
`zynq-arm-cosim.dtb` has nodes for most of these: the PS **GPIO** (`0xE000A000`), **SPI0/SPI1**
(`0xE0006000`, `0xE0007000`), **CAN0/CAN1**, **USB0/USB1**, the **device configuration** block
(`0xF8007000`), the DDR controller (`0xF8006000`), the OCM controller (`0xF800C000`), the eFuse
(`0xF800D000`), the **L2 cache controller** (`0xF8F02000`) and the **SCU watchdog**
(`0xF8F00620`; the private-timer window ends at `0xF8F0061F`). A read of such an address returns 0
and a write is dropped, with no abort. Consequences, all seen in the table: `xgpiops` reads back 0
after writing 1; `xspips` and `xcanps` self tests read back 0; `XDcfg_SelfTest` sets CTRL.NIDEN and
reads back 0; the SCU watchdog never expires, so `xscuwdt_*` spin forever; the BSP's L2 cache
enable writes into nothing (harmless, but the L2 is unmodelled). Gate: `bsp_apps.rs`
`DEVIATIONS`.

**D2. XADC returns zeros.** `xadcps_polled_printf_example` prints "Current Temperature is
-273.149 Centigrades" and 0.000 V for VCCPINT, VCCPAUX and VCCPDDRO (raw sample 0). On hardware
the die temperature is around 30-60 C and VCCPINT is about 1.0 V. The driver and the register
interface work (the example reaches its success line, which only checks that reads complete), the
data do not.

**D3. The A9 MPCore timers run at 100 MHz, not 333 MHz.** Measured with the probe over 10 ms of
simulated time: the global timer counted 1,000,094 and the private timer 1,000,094 ticks, i.e.
100.009 MHz. The BSP's `COUNTS_PER_SECOND` is `XPAR_CPU_CORTEXA9_0_CPU_CLK_FREQ_HZ / 2` =
333,333,343 for this platform (CPU 666.67 MHz). So every delay the BSP derives from them
(`sleep()`, `usleep()`, `XTime_GetTime` deadlines, the SCU timer load values) is about 3.3 times
longer in simulated time than on silicon at that clock. `bsp_emacps_intr_dma` sleeps for seconds
between steps and therefore needs about 40 simulated seconds. This was already noted for the
global timer in STATUS.md (Ethernet limits); it is now measured for the private timer too.

**D4. No `ps7_init` / FSBL.** The applications start at SLCR reset state (the QEMU SLCR model's
reset values, for example `APER_CLK_CTRL` = `0x01FFCCCD`), without PLL/clock/MIO programming and
without a DDR controller (RAM is simply there). Applications that depend on `ps7_init` results
(real clock frequencies, MIO muxing) cannot be judged by this; nothing in the table did.

## Not covered yet

* **lwIP applications and FatFs** (`lwip_echo_server`, `xilffs`): need extra BSP libraries and a
  second platform generation. Not attempted. The GEM driver's DMA example and the raw SD example
  cover the same controllers at register level, not the stacks.
* **Flash and EEPROM paths**: the QSPI/I2C/SPI selftests are register-level only; the flash polled
  and EEPROM examples need devices on the bus and were not built.
* **USB, CAN, SPI, GPIO, devcfg, SCU watchdog, L2C** behaviour: absent from the machine (D1), so no
  claim is possible; a native PS model (P5) or a different QEMU would be needed.
* **Multicore, cache coherency with DMA** (QEMU does not model the caches, so the
  `Xil_DCacheFlushRange` / invalidate calls in the drivers cannot be exercised for effect).
* Anything compared with hardware.
