# ADR-032: Native RTL front end (`rtl-frontend`), before the native RTL engine

Status: **Accepted** (milestone P6, front end only). Date: 2026-10-17.

## Context

Prompt §9.1 asks for Verilog-2001 and the synthesizable SystemVerilog subset, and for the tool
to print file, line and construct for anything unsupported. §9.2 lists a native subset engine
(phase P6) that needs no external tool. Until now every RTL design went through Vivado XSim,
and the only language checks were XSim's (`xvlog`/`xelab`), quoted from `build.log`. The one
header parser in the tree (`sim-api::tbgen::parse_module`) reads ports only and does not
understand bodies.

The P6 engine has to be built on an AST, and a wrong AST makes every later result wrong. The
front end is therefore built and tested first, on its own, against the repository's own sources.

## Decision

1. A new pure-Rust crate, `crates/rtl-frontend`, with `#![forbid(unsafe_code)]` and no
   dependencies (`serde` is optional, behind a feature, for the CLI's JSON). It has four parts:
   - `lexer`: tokens with file, line, column, and the whitespace and newline flags that macro
     bodies need;
   - `pp`: the preprocessor, which owns the macro table, the conditional stack and `include`;
     expansions carry the use site as their position;
   - `parser`: recursive descent into the AST (`ast`). Every loop consumes a token or stops.
     Unsupported constructs produce a `Diagnostic` (file, line, column, construct, message) and
     the parser resynchronises at `;` or at a block-closing keyword;
   - `elab` (with `consteval`): parameter resolution with overrides, generate unrolling into an
     instance tree (`label[i]` paths), widths, and checks for undefined modules, ports,
     identifiers and functions. `consteval` evaluates constants on 128-bit values with the
     Verilog sizing and signedness rules, `$clog2` and constant functions.
2. **Budgets.** Every pass takes units from a `Budget` (default 20 million steps). A malformed
   input stops with a `budget` diagnostic instead of running on. Macro nesting and include depth
   are capped as well.
3. **The subset is defined by the diagnostics, not by a list of accepted words.** A construct is
   supported when a test shows it parses to the AST. Everything else is named (see
   `docs/RTL_SUBSET.md`). Reals and the DPI-C, class, interface and package constructs are
   reported, not parsed.
4. **Pinned corpus.** `tests/corpus.rs` parses every `.v`, `.sv`, `.vh`, `.svh` under
   `zynqsim/{fixtures,examples,tests}` and compares the set of files with diagnostics, and the
   constructs they name, with a list in the test source. A change in either direction fails the
   test. Progress is therefore visible in the diff.
5. **Fuzzing in the normal suite.** 5000 seeded mutations of repository sources (deletions,
   insertions of token fragments, cross-file splices, line duplication) must not panic and must
   stay within the budget. The first run found a lexer loop, which is now a regression test.
6. **CLI.** `zynqsim rtl-check FILE... [--top M] [-I DIR] [-D NAME=VAL] [--json]`. Diagnostics go
   to stdout as `file:line:col: construct: message`; `--json` adds the module list and, with
   `--top`, the instance tree and port lists. Exit codes: 0 clean, 1 diagnostics, 2 usage.

No simulation happens in this crate. "Verified" in `docs/STATUS.md` means the parser and
elaborator behave as the named tests say; it does not mean that the results agree with XSim.

## Consequences

* The front end is the input of the P6 engine. The engine can be built on the AST without
  re-deriving the grammar, and its subset is exactly what the front end accepts.
* A design that parses clean is not thereby correct. The next step, if P6 goes on, is a
  differential check of elaboration (instance tree, widths) against `xelab` on the corpus.
* The pinned list must be regenerated by hand after an intended change. That is deliberate:
  it keeps the diff honest.
* The parser is written by hand (about 2,700 lines in `parser/`). It is larger than a grammar
  generator's output would be, but every construct's diagnostic is under our control, and the
  parser has no build-time dependency.
* Macro expansion is textual at token level. Two cases are not exact: token pasting that is
  not the `'d` form after a macro (`` `W'd4 ``, handled), and macros that expand to partial
  statements (they parse only if the whole statement is in one expansion, as in standard use).

## Alternatives considered

* **`sv-parser` or `tree-sitter-verilog` crates.** Both would add dependencies (one with a large
  tree, one with C code, which the project rules forbid). Their error reporting would not give
  the construct names the spec asks for.
* **Use XSim's elaboration for the diagnostics.** That is the current behaviour (quoted from the
  build log) and stays as the authority for the XSim backend. It needs Vivado, which the P6
  goal does not.
* **Accept more and check later.** Rejected: a permissive parser would let the engine see
  constructs it cannot simulate, and the honesty contract (§1) forbids that.
